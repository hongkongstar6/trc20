转账流程
1. 校验发起方余额
   ├─ 查询发起方 USDT 余额是否满足转账金额
   └─ 查询发起方 TRX 余额（确保够支付最低手续费或无能量时的扣费）

2. 模拟交易与能量计算
   ├─ 调用 triggerConstantContract 模拟转账，获取精确预估 energy_used
   ├─ 能量需求 = energy_used * 1.05 (安全系数) - 发起方现有可用能量
   └─ 若需补充能量/带宽，查询实时租金并计算租赁方案

3. 能量 & 带宽准备
   ├─ 向第三方能量平台下单租赁
   └─ 轮询发起地址资源，确认租赁能量已到达发起账户

4. 构建与广播交易
   ├─ 构建未签名交易对象（TRC-20 transfer(to, value)）
   ├─ 使用本地私钥签名交易
   └─ 广播交易至波场网络 (broadcastTransaction)

5. 交易结果上链确认
   ├─ 轮询获取交易回执 (getTransactionInfoById)
   └─ 校验 contractResult 为 SUCCESS 且能量消耗正常

转账失败处理策略：
USDT 转账失败不仅会导致业务中断，还可能伴随手续费损失或资金暂扣。处理转账失败的核心原则是：根据链上失败原因（Receipt Status / Result）进行分类处置。
一、 转账失败的 4 种常见原因及处理策略
1. 能量不足导致的失败 (OUT_OF_ENERGY / REVERT)
这是波场转账中最常见的失败原因。
• 原因：租赁的能量数额不够（例如收款方余额为 0 耗费了 6.5 万能量，但只租了 3.2 万），或者链上动态能量上浮导致能量耗尽。
• 损失情况：已消耗的能量和扣除的 TRX 无法退回，但 USDT 资产仍在发起方账户中，没有减少。
• 处理动作：
补足能量（建议按预估量的 1.05~1.1 倍 租赁）。
重新发起转账（生成新的交易，不能直接重播旧交易）。
2. 交易未广播成功 / 网络超时
• 原因：节点 RPC 报错、网络波动导致 broadcastTransaction 失败或未及时响应。
• 损失情况：未消耗任何 TRX/能量，资金未变动。
• 处理动作：
防重推检查：再次请求节点 API（getTransactionById），确认该交易 ID 是否已上链。
若链上查不到该 TxID，且超过波场交易有效期（通常为 60 秒），方可发起重试。
3. 发起方 USDT 余额不足 / 合约冻结 (REVERT)
• 原因：在构建交易到广播期间，发起方账户余额被其他操作划走；或地址被 USDT 官方黑名单限制。
• 损失情况：可能消耗了少量能量/TRX，USDT 未转移。
• 处理动作：
校验本地逻辑，更新发起方真实余额。
弹出具体提示（如“余额不足”或“账户状态异常”），告警并终止重试。
4. 能量租赁失败或能量未及时到账
• 原因：第 3 步去第三方平台购买能量，虽然 API 返回成功，但波场链上能量授权（Delegate）延迟，导致广播时使用的是发起地址原有的 TRX 扣费（甚至因为 TRX 不够直接失败）。
• 处理动作：
租赁能量后，务必轮询/校验发起账户的 AccountResource，确认能量到账后再触发签名与广播。
